# 组织与审计模型

本文档固化 P3 企业内部投产所需的业务概念：部门、模型权限覆盖层、花费速率限制、操作审计、主动告警、管理侧幂等、用量数据保留与归档。术语与枚举取值同步登记在 `docs/glossary.md`，本文档记录数据模型、归属关系、状态转换与口径规则。

## 一、部门

### 概念定义

部门是组织内部的成本归属单元，用于费用分摊与预算对比。部门只有一层，不构成上下级树；用户归属 0 个或 1 个部门。

**部门不持有积分余额，不参与扣费链路。** 一次 /v1 调用仍然只从用户余额扣减，积分流水的主体仍然只有用户一方。给部门下发预算的实际动作是"对该部门成员批量发放积分"。部门的月度预算是报表中的对比目标值，超出只触发告警，不拦截调用。

这条边界的作用是把计费内核（余额行锁、`余额 == 流水之和` 不变式、预扣—结算—退款三阶段、`tzl reconcile` 对账）完整保留在单主体记账形态下。引入部门积分池会使上述每一处都要改为双主体，代价远超部门预算带来的收益。

### 数据模型

`departments` 表：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | BIGSERIAL | 主键 |
| `name` | TEXT UNIQUE | 部门名称 |
| `code` | TEXT | 成本中心编码，对接财务系统用；非空时唯一 |
| `owner_user_id` | BIGINT NULL | 部门负责人，指向 `users`，`ON DELETE SET NULL` |
| `monthly_budget_credits` | BIGINT | 月度预算积分，0 表示未设预算，不做超预算告警 |
| `allowed_models` | JSONB NULL | 部门级模型策略，见第二节 |
| `status` | TEXT | `enabled` / `disabled` |
| `note` | TEXT | 备注 |

`users.department_id` BIGINT NULL，`ON DELETE RESTRICT`：部门仍有成员时不允许删除，必须先转出成员。

### 归属关系与快照规则

`usage_logs.department_id` 与 `credit_ledger.department_id` 记录**记账时点**用户所属部门的快照，而不是查询时 join `users` 取当前部门。

不做快照会导致：某人从研发部转到销售部后，其在研发部期间产生的全部消费会在报表中整体迁移到销售部，与财务已经出账的历史分摊对不上，且无法复原。快照使已出账月份的报表口径永久稳定。

未分配部门的用户，快照值为 0；报表中 `department_id = 0` 显示为"未分配"一行。

### 状态转换

| 当前状态 | 事件 | 目标状态 | 前置条件 | 副作用 |
|---------|------|---------|---------|--------|
| —— | 管理员创建 | `enabled` | 名称未占用；编码非空时未占用 | 记审计 `department.create` |
| `enabled` | 管理员停用 | `disabled` | 无 | 不能再分配新成员；现有成员保持归属与调用能力不变 |
| `disabled` | 管理员启用 | `enabled` | 无 | 恢复可分配 |
| 任意 | 管理员删除 | 记录消失 | 成员数为 0 | 已产生的用量日志与流水中的部门快照保留原 ID，报表显示为"已删除部门 #N" |

部门停用刻意不连带禁用成员账号：部门是成本归属维度，不决定成员能否调用 API，停用部门只表示"不再作为归属选项"。需要停止某人调用时禁用其账号。

### 负责人的查账资格

`owner_user_id` 是唯一由部门归属派生出的权限。担任负责人的账号可经 `/api/dept` 只读查看本部门的消费、预算进度与成员用量；无任何写操作。

该资格刻意不落在 `users.role` 上。角色一经授予就与部门归属脱钩：转岗后仍保留原部门的查账能力，撤销要靠人记得改角色；且单值的角色字段无法表达同一人负责两个部门。以归属关系为准则没有这两个问题——改部门的负责人字段即完成授予与撤销，且天然支持一人多部门。代价是每次请求都要按 `department_id` 校验一次归属，不能只在中间件里判角色，故本组端点逐个显式校验。

负责人视图不返回 `credits_cost` 与 `margin`：那是网关向上游支付的成本与差额，属于网关运营方的口径，与部门的费用分摊无关，且会暴露上游供应商构成。同理不开放按渠道聚合的维度。

### 报表口径

按部门聚合一律使用用量日志上的部门快照，不 join `users`。月度预算对比取自然月（服务器时区）的 `credits_charged` 合计与 `monthly_budget_credits` 相比。部门负责人视图与管理员的全站报表读同一套聚合，只是强制加上本部门的筛选条件，因此两处口径一致。

## 二、模型权限覆盖层

现状是模型白名单只存在于 API Key 上，而 Key 由用户自己创建和修改，管理员无法约束某人可调用的模型。

引入两层管理员可控的策略，与用户自管的 Key 白名单构成三层：

| 层 | 字段 | 归谁维护 |
|----|------|---------|
| 部门策略 | `departments.allowed_models` | 管理员 |
| 用户策略 | `users.allowed_models` | 管理员 |
| 密钥白名单 | `api_keys.allowed_models` | 用户本人 |

**解析规则：各层都只能收窄，不能放宽；有效可调用模型集合 = 三层的交集。** 某层为 NULL 或空数组表示该层不施加限制，不参与取交集。

请求模型不在有效集合内时返回 403，错误码 `model_not_allowed`（沿用现有错误码，不新增）。

策略内容解析失败（JSONB 非字符串数组）时**拒绝调用并告警**，不再按现行实现放行。放行等于配置写错就静默失效，与设置白名单的意图相反。同一处理原则适用于密钥的来源 IP 白名单。

## 三、花费速率限制

`users.daily_spend_limit` BIGINT，0 表示不限制。约束的是单个用户单个自然日（服务器时区）内的累计扣费积分，防止单人在一天内耗尽本应覆盖整季度的额度。

计数落在 `daily_spend` 表：

| 字段 | 说明 |
|------|------|
| `user_id` | 用户 |
| `day` | 自然日（DATE） |
| `credits` | 当日累计净扣费 |

主键 `(user_id, day)`。计数在 `billing.Service` 的余额调整事务内同步 upsert，与积分流水同源，因此不会出现"扣了积分但没计数"。预扣计正、退款与结算退差计负，与 `credit_used` 的累计口径一致。

请求预扣前检查：当日已扣 + 本次预扣 > 上限时拒绝，错误码 `daily_spend_limit_exceeded`，HTTP 429。

部门层面不设每日花费上限，只有月度预算告警。部门级硬限制需要在每次请求时聚合全部成员的当日消费，代价与收益不匹配；确需硬限制时对成员逐个设上限。

## 四、操作审计

### 概念定义

操作审计记录管理侧的写操作与全部账号的认证事件，用于回答"谁在什么时候改了什么"。审计记录只追加，不提供更新与删除接口。

审计不覆盖：读操作、/v1 中继调用（已有用量日志承担）、用户自助的密钥增删改（属用户自身资源，非管理动作）。

### 数据模型

`audit_logs` 表：

| 字段 | 说明 |
|------|------|
| `id` | 主键 |
| `operator_id` | 操作人用户 ID，0 表示系统自身（定时任务、启动自检） |
| `operator_name` | 操作人用户名快照，操作人账号后续被改名或删除后仍可读 |
| `operator_role` | 操作时的角色快照 |
| `action` | 动作枚举，取值见 `docs/glossary.md` |
| `target_type` | 对象类型：`user` / `department` / `model` / `channel` / `redemption` / `setting` / `session` / `audit` |
| `target_id` | 对象 ID，无具体对象时为 0 |
| `target_name` | 对象名称快照 |
| `result` | `success` / `failure` |
| `before` / `after` | 变更前后的字段摘要（JSONB），只含本次涉及的字段 |
| `client_ip` | 来源 IP |
| `request_id` | 请求标识，与访问日志关联 |
| `message` | 补充说明，失败时记录原因 |
| `created_at` | 时间 |

索引：`(created_at DESC)`、`(operator_id, created_at DESC)`、`(target_type, target_id, created_at DESC)`、`(action, created_at DESC)`。

### 敏感字段处理

`before` / `after` 中的密码哈希、上游渠道密钥、SMTP 密码、Webhook 密钥一律记为 `"***"`，只表达"该字段被修改过"，不记录任何值（含旧值）。兑换码明文不入审计。

### 写入方式

审计记录由各写操作处理函数在业务成功后显式写入，而不是由中间件按路由统一生成。中间件拿不到对象名称与变更前后的字段，只能记"某人调用了某个 URL"，无法满足"谁改了某模型单价"这类追溯。

审计写入失败不影响主业务返回，但必须记 ERROR 级日志。

### 保留期

`audit_log_retention_days` 默认 180 天，覆盖等保二级对安全审计记录留存六个月的要求。定时任务按保留期清理超期记录，清理动作本身写一条 `audit.purge`（`operator_id = 0`），使"审计记录被清理"这件事本身可追溯。设为 0 表示不清理，其余取值不得少于 30 天——数据库触发器拒绝删除写入未满 30 天的审计记录，保留期短于该值会让清理任务被数据库拒绝，因此设置项在写入时即挡掉这类取值。

### 积分流水补操作人

`credit_ledger.operator_id` 记录发放/扣回的管理员 ID，0 表示非管理动作（消费、退款、兑换）。现行实现把操作人塞在 `ref_type='admin_user'` + `ref_id` 里，语义与"引用对象"混用，查询时需要按 `ref_type` 分支判断。

## 五、主动告警

### 事件与触发

| 事件类型 | 触发条件 | 严重度 |
|---------|---------|--------|
| `channel_auto_disabled` | 渠道因连续致命错误被自动禁用 | 严重 |
| `reconcile_failed` | `tzl reconcile` 发现余额与流水不一致 | 严重 |
| `usage_log_dropped` | 用量日志队列丢弃计数由 0 变为非零 | 严重 |
| `orphan_precharge_found` | 孤儿预扣回收单轮处理条数非零 | 提醒 |
| `department_over_budget` | 部门当月消费超过月度预算 | 提醒 |
| `backup_failed` | 备份脚本执行失败 | 严重 |

### 去重

同一 `dedup_key` 在抑制窗口（`alert_dedup_window_sec`，默认 3600 秒）内只投递一次，窗口内的重复事件落库并标记为 `suppressed`。去重键按事件类型构造，例如渠道自动禁用为 `channel_auto_disabled:<channel_id>`。

没有去重会让一个持续故障的渠道在探测周期内反复触发，把告警通道刷成噪声，管理员随后会忽略全部告警。

### 事件状态转换

| 当前状态 | 事件 | 目标状态 |
|---------|------|---------|
| —— | 事件产生且不在抑制窗口内 | `pending` |
| —— | 事件产生但命中抑制窗口 | `suppressed` |
| `pending` | 至少一条通道投递成功 | `sent` |
| `pending` | 全部已配置通道投递失败且重试次数耗尽 | `failed` |

告警事件表同时是投递失败的排查依据——管理员报告"没收到告警"时，需要能区分"没触发"与"触发了但发不出去"。

### 通道

**Webhook**：向管理员配置的 HTTP 地址 POST 告警内容。为避免管理员自行拼装报文格式，内置以下预设，按 `alert_webhook_format` 选择：

| 取值 | 目标 | 报文形态 |
|------|------|---------|
| `generic` | 任意接收端 | 原始 JSON（事件类型、严重度、标题、正文、时间、明细） |
| `dingtalk` | 钉钉群机器人 | markdown 消息；`alert_webhook_secret` 非空时按钉钉加签规则追加 `timestamp` 与 `sign` 查询参数 |
| `feishu` | 飞书群机器人 | 富文本 post 消息；`alert_webhook_secret` 非空时按飞书签名规则填充 `timestamp` 与 `sign` 字段 |
| `wecom` | 企业微信群机器人 | markdown 消息 |
| `slack` | Slack Incoming Webhook | `text` + `blocks` 消息 |

**SMTP 邮件**：向 `alert_email_to`（逗号分隔的多个收件人）发送告警邮件。SMTP 密码经 AES-GCM 加密后存入设置表，读取接口一律返回掩码，不回显明文。该通道同时是后续自助找回密码功能的前置能力。

两条通道都配置时并行投递，任一成功即视为已送达。都未配置时事件仍然落库，状态直接为 `failed` 并在服务日志中提示未配置告警通道。

## 六、管理侧幂等

发放积分端点现状是重复提交会各自记账，误触或网络重试造成积分重复发放，且无撤销入口。

引入可选的 `idempotency_key`：调用方传入后，服务端以 `admin:<idempotency_key>` 写入流水的 `request_id` 字段，命中现有的 `(request_id, entry_type)` 部分唯一索引即判定为重放，直接返回首次结果而不再记账。批量发放时每个用户一条流水，键为 `admin:<idempotency_key>:<user_id>`。

`admin:` 前缀用于隔离管理侧幂等键与中继侧请求标识两个命名空间，防止两者取值碰撞后互相判定为重放。

不传 `idempotency_key` 时行为与现状一致（各自记账），保持既有调用方兼容。

## 七、用量数据保留与归档

用量日志随运行时间线性增长，而全部按日、按用户、按部门、按模型的报表都直接聚合原表，查询会逐月变慢。

引入 `usage_daily_rollup` 按日聚合表，维度为 `(day, user_id, department_id, model_name, channel_id)`，度量为请求数、各类 token 数、扣费积分、成本积分。定时任务在次日汇总前一日及更早尚未汇总的数据，只汇总 `status = 'settled'` 的记录，与现行报表口径一致。

汇总时点延后到自然日结束之后，避开孤儿预扣补偿改写日志状态的窗口。

报表查询按日期范围拆两段：已汇总日期读聚合表，当日读原始日志，合并后再聚合。原始日志仅用于明细查询与导出，按 `usage_log_retention_days`（默认 90 天，0 表示不清理）清理，清理前校验该日期已完成汇总。
